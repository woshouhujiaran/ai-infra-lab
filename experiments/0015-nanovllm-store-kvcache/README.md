# 0015 — nano-vllm `store_kvcache` (Triton KV-cache write kernel)

- **Upstream**: [GeeeekExplorer/nano-vllm](https://github.com/GeeeekExplorer/nano-vllm) (submodule `upstream/nano-vllm`, commit `bb823b3`). `nanovllm/layers/attention.py` is imported unmodified through `lab/nanovllm_shim.py`. `flash_attn` cannot be installed on Windows, so it is stubbed; only the KV write is exercised.
- **Component**: `store_kvcache_kernel` + `store_kvcache` in `layers/attention.py`. Every attention layer calls it once per step to write the new K/V rows into the paged cache at `slot_mapping`. It launches one program per token, loads `tl.arange(0, D)` with D = num_kv_heads × head_dim, skips slot `-1`, and stores at `slot * D` using the int32 slot ids that `ModelRunner` builds.
- **Hardware**: RTX 4060 Laptop 8 GB (32 MB L2, 256 GB/s theoretical DRAM), torch 2.14.1+cu126, triton-windows 3.8.0, memory capped at 60% by `lab/gpu_guard.py`. Peak allocated memory was 1.26 GB in the main process. The overflow children use a 4 GiB int8 cache.
- **Run**: `.venv\Scripts\python.exe experiments\0015-nanovllm-store-kvcache\run.py` (about 5 min, of which 2 min are the overflow child processes).

## Question

The write kernel is a few lines of Triton on nano-vllm's hot path. It runs once per layer per step, in eager mode for prefill and inside CUDA graphs for decode. Is it exact for the inputs it actually receives: a strided V slice of the fused qkv output, and `-1` padding from CUDA-graph batch buckets? Which KV shapes can it handle at all? Can its int32 `slot * D` offset overflow, and what happens if it does? How does it compare with the obvious torch replacements (`index_put_`, `index_copy_`, `torch.compile`) and with a masked, int64-offset, multi-token-per-program rewrite, both on the GPU and including Python launch cost?

## Setup

- **Exactness**: fp32 / fp16 / bf16 at D ∈ {128 (2×64), 512 (8×64), 1024 (8×128), 4096 (32×128)}. Two patterns: a 64-token decode batch whose last 16 slots are `-1`, and a 1000-token prefill laid out in 256-slot blocks. K is contiguous. V is the strided slice of a Qwen3-style fused qkv tensor, which is what `Qwen3Attention` passes. Caches start as random data, and the whole cache is compared bitwise with a torch reference that skips `-1`.
- **Non-power-of-two D**: 192 (3×64, the SmolLM2-135M KV shape), 320 (5×64, SmolLM2-360M), 768 (12×64, GPT-2 small), 384 (3×128), 2560 (32×80, phi-2) and 3072 (32×96, Phi-3-mini).
- **Overflow**: a child process builds `kv_cache[2 layers, S, D=1024]` the way `ModelRunner.allocate_kv_cache` does: each layer's `k_cache` is a view into one big tensor. S is one block past 2^31 / D. It writes one token to layer 1 and then scans the whole cache to find where the token landed. The cache is int8 so that 2^31 elements fit in 8 GB. The kernel is dtype-agnostic and the offset arithmetic counts elements, so the result carries over to bf16.
- **Performance**: bf16, a 128 MiB K cache plus a 128 MiB V cache, D ∈ {128, 256, 512, 1024, 4096} plus the non-power-of-two 320 and 2560, and N ∈ {1, 16, 64, 256} decode tokens (random distinct slots) and {1024, 4096, 16384} prefill tokens (whole blocks).
  - Variants: `upstream`; `masked_n1` (BLOCK_D = next_pow2(D), mask, int64 offsets, 1 token per program); `masked_tiled` (same with min(64, 4096 / BLOCK_D) tokens per program); `torch_index_put` (`k_cache.view(-1, D)[slot_mapping] = k`); `torch_index_copy` (with `slot_mapping.long()`); `torch.compile(index_put)`; and `copy`, which writes the same bytes into the first N rows with no scatter.
  - Two timing modes. **CUDA-graph** time replays 200, 100 or 20 back-to-back calls from a captured graph; this measures GPU time only, which is how nano-vllm runs decode. **Eager** wall time includes the Python launch, which is how prefill runs. Each cell interleaves all variants for 3 rounds and reports medians. The GPU is warmed before each cell, because `torch.compile` compiling with the GPU idle had inflated the first cell 2–4× in an earlier run.
  - Every timed variant was checked for exact output in every cell.

## Findings

1. **Upstream is bit-exact in all 24 cases**, for every dtype and D, with the strided V view and with `-1` padding: no other cache row is touched. The naive torch replacement is not a drop-in. `index_put_` treats `-1` as "last row", so in all 12 padded cases it overwrote cache slot 8191 (the last slot of the last block) with a padding row. In nano-vllm that block can belong to a live sequence once the cache fills.
2. **The kernel cannot compile when D is not a power of two.** All 6 such shapes fail with `CompilationError: arange's range must be a power of 2`. Every Qwen3 checkpoint nano-vllm supports has D = 8×128 or 4×128, and stays a power of two under tensor parallelism, so nano-vllm itself is unaffected. Porting the layer to models such as SmolLM2, GPT-2, phi-2 or Phi-3 breaks it. A masked BLOCK_D = next_pow2(D) version is exact for all of them and runs as fast as `torch.compile`: 0.97–15 µs per decode or 1k-prefill call, and 233–267 GB/s at large N.
3. **The int32 `slot * D` overflows silently into another layer's cache.** With D = 1024, a layer-1 write to slot 2,097,155 (slot × D = 2^31 + 3072) landed in **layer 0, slot 259**: no error, wrong data in a different layer. Slot 2,097,151, just below the boundary, lands correctly. The same kernel with an int64 `slot_mapping`, the masked rewrite (`.to(tl.int64)`) and torch `index_put_` all land correctly.
   - The limit is 2^31 elements per layer per K or V. That works out to 2 · layers · 2^31 elements of total KV per GPU, independent of D and TP size: 224 GiB in bf16 (112 GiB in fp8) for 28-layer Qwen3-0.6B / 1.7B, and up to 512 GiB for Qwen3-32B.
   - So it is latent on current ≤ 192 GB GPUs. A ~288 GB GPU running a 28-layer Qwen3 at nano-vllm's default `gpu_memory_utilization=0.9` would size its cache past the limit. `BlockManager` hands out low block ids first and recycles freed blocks to the back of the queue, so the top slots are used once the cache is nearly full or after churn.
4. **In the decode path (CUDA graph), upstream sits at the launch floor, and torch replacements are 3–6× slower.** For N ≤ 256 and D ≤ 1024, upstream takes 0.96–2.2 µs per call. `index_put_` is 4.5–6.5× slower (4.9–12.7 µs; two indexing kernels plus index preprocessing), `index_copy_` is 3.1–4.5× slower, and `torch.compile` is 0.85–1.6×. With 28 layers per Qwen3-0.6B step, upstream costs about 30–60 µs per step, against 140–350 µs for `index_put_`. The masked int64 rewrite with 1 token per program costs nothing: it is 0.90–1.09× of upstream in all 35 power-of-two cells.
5. **One token per program is wasteful only for small D during prefill.** At D = 128 (2×64, the Qwen2.5-0.5B KV shape), packing tokens into a 4096-element tile makes prefill 1.27× / 1.62× / 2.33× faster at 1k / 4k / 16k tokens (28.3 → 12.1 µs at 16k; `torch.compile` gets 16.4). At D = 256 it helps 1.12–1.18×. At D ≥ 512 it gives 0.90–1.03×. During decode (N = 16–256, D ≤ 1024) the tiled version is 4–20% slower, so the best choice is 1 token per program for decode and tiles for small-D prefill.
6. **Once the working set exceeds L2, everything is DRAM-bound, and `index_put_` still loses 12–20%.**
   - For working sets of 64 MiB or more, the Triton kernels, `torch.compile` and plain `copy_` all run at 227–239 GB/s (89–93% of theoretical). `index_put_` reaches 195–208 GB/s (1.12–1.20× slower; 666 vs 584 µs at D = 1024, N = 16k), and `index_copy_` is 1.02–1.05× slower.
   - In the L2-resident middle range (1–32 MiB moved), upstream reaches 0.44–1.44 TB/s effective, while `index_put_` reaches 107–260 GB/s (2.0–5.9× slower).
   - Below about 1k tokens, every variant is launch-bound at roughly 1 µs per kernel, so the 2-kernel `copy` baseline is about 2× slower than the 1-kernel scatter.
7. **Eager prefill calls are dominated by the Python launch.** Medians are 28–71 µs per Triton call (median of medians 48 µs), 94–205 µs for `index_put_`, 53–169 µs for `index_copy_` and 92–166 µs for `torch.compile` (guards plus wrapper), against 1–15 µs of GPU work. Background load (about 39% CPU on a hybrid i9-13900H) made the eager numbers swing by up to 2× between rounds, so only the ordering is reliable: the Triton launch is 2–3× cheaper than the torch alternatives. Per prefill step that is about 1.3 ms of launch overhead across 28 layers, versus about 4 ms for `index_put_`.

Takeaway: upstream `store_kvcache` is correct and as fast as anything tried here for nano-vllm's own Qwen3 shapes, and it is 3–6× faster per decode step than the torch one-liners. Those one-liners also mishandle `-1` padding by silently writing into the last cache slot. It has two latent limits. It fails to compile for KV widths that are not a power of two, and its int32 `slot * D` silently corrupts the previous layer's cache once a layer holds 2^31 elements. Both are fixed at no measured cost by a masked BLOCK_D = next_pow2(D) load and casting `slot` to int64 (or building `slot_mapping` as int64). For small-D models, packing several tokens per program makes prefill writes up to 2.3× faster.
